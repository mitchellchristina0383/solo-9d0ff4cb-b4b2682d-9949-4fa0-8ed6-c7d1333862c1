# OOM 归属核对台

Linux 服务被 OOM 杀死后，值班员需要判断是**服务自身 cgroup 超限**还是**整机内存不足**，
并定位到具体是哪一次服务运行。本工具用 Flask + SQLite 实现：

1. 分开导入一台主机的**运行记录**与**内核 OOM 摘要**两份 CSV；
2. 自动把每个 OOM 事件归属到唯一匹配的运行记录；
3. 值班员在页面上确认归属与触发范围后派查；
4. 补录或按编号更正数据后自动重核：归属或触发范围变化的事件，其原确认被撤销，
   旧页面提交的确认请求被拒绝，其他事件不受影响；
5. 全部结论与确认状态落 SQLite，重启后可继续查；
6. 值班员在每个 OOM 事件页上传/下载**现场诊断包**，按可配置上限留存，
   内容去重、跨事件共用，并按确认状态保护与 FIFO 清退。

## 运行

### Docker Compose（推荐）

```bash
docker compose up -d --build
# 打开 http://localhost:8000
```

- 数据保存在命名卷 `oom-data`（容器内 `/data/oom.db`，诊断包临时分片在
  `/data/blob-spool`），重启、重建容器均不丢。
- 诊断包留存上限用环境变量 `OOM_BLOB_QUOTA` 配置，默认 `100M`（100 MiB），
  支持 `100M`、`2g`、纯字节数；`OOM_BLOB_SPOOL` 可覆盖临时分片目录。
- 可用 `SECRET_KEY=xxx docker compose up -d` 覆盖会话密钥。

### 本地开发

```bash
pip install -r requirements.txt   # 仅运行只需 flask
python run.py                     # http://localhost:8000
```

数据库路径用环境变量 `OOM_DB` 指定，默认 `<instance>/oom.db`。

## CSV 格式

UTF-8 编码，首行为表头。时刻均为**该次启动后的毫秒**。

**运行记录** `run_no,boot_id,pid,cgroup,start_ms,end_ms`

- `run_no` 运行号（全局唯一）；`boot_id` 主机启动 ID；`pid` 主进程 PID；
- `cgroup` 服务所在 cgroup；`[start_ms, end_ms)` 为起止时刻，**左闭右开**。

**OOM 摘要** `event_no,boot_id,pid,cgroup,time_ms,scope`

- `event_no` 事件号（全局唯一）；`pid` 被杀 PID；`cgroup` 被杀进程所在 cgroup；
- `scope` 触发范围：`memcg`（触发组）或 `host`（整机）。

导入按编号 upsert：**新编号 = 补录，已有编号 = 更正**。任一行不合法则整文件不写入
（原子导入）。也可在「运行记录」「OOM 摘要」页面按编号单条更正/补录。
样例见 `sample_data/`。

## 归属规则

事件 E 匹配运行记录 R 当且仅当：

```
R.boot_id = E.boot_id  AND  R.pid = E.pid  AND  R.cgroup = E.cgroup
AND  R.start_ms <= E.time_ms < R.end_ms
```

- **恰好 1 条匹配** → 页面列出运行号与触发范围，值班员确认后派查；
- **0 条或多条** → 标为「待核」（并显示候选数），不能确认。

PID 复用由「启动 ID + 左闭右开时段」区分；同 PID 不同 cgroup 由 cgroup 字段区分；
跨重启由 boot_id 隔离。

## 确认、撤销与防旧页面

- 每个唯一匹配计算指纹 `sha256(event_no|run_no|scope)`，确认按钮携带该指纹提交。
- 任何导入/更正后**全量重核**所有事件：归属（运行号）或触发范围（scope）变化
  → 该事件的有效确认被撤销（保留历史与原因），页面提示；指纹不变则确认保留。
- 确认请求到达时重新比对当前指纹：不一致（即旧页面）→ 拒绝并提示刷新。
- 数据库部分唯一索引保证同一事件至多一条有效确认（并发兜底）。

## 现场诊断包：上传、共用与留存清退

入口：事件核对页 / OOM 摘要页每个事件的「诊断包」链接，或
`/events/<event_no>/packages`。该页可上传、下载并查看当前留存用量。

**存储模型（内容寻址）**

- `blobs` 表按 sha256 内容存包：同一份内容全库只存一份字节；
- `event_attachments` 表做事件↔包挂载：每个事件至多一个附件，同一个包可挂到
  多个事件下。因此**相同内容挂多个事件只按一份计字节**；
- 重复上传相同内容到同一事件不产生新数据；上传不同内容则替换该事件附件，
  旧包若再无任何挂载立即删除（字节释放）。

**留存上限与清退**

- 上限由 `OOM_BLOB_QUOTA` 配置（默认 100 MiB）；HTTP 请求体超过上限直接 413。
- **保护**：已确认派查（存在 active 确认）的事件，只要还挂着某个包，该包就不能
  被清退。保护只约束 FIFO 清退，不影响该事件本人主动替换自己的附件。
- **清退顺序**：新包放不下时，按首次入库顺序（`blobs.id` 自增）清退未受保护的
  其余包，腾够即停，并移除被清退包的**所有**事件挂载。
- **接收中可确认**：接收文件期间仍允许确认派查；能否清退一律以**新包入库事务
  开始那一刻**的确认状态为准（`BEGIN IMMEDIATE` 取写锁后计算保护集合）。
- **整单原子**：新包入库、挂载、整批清退在同一个 SQLite 事务内一并生效；
  腾不够空间则整单拒收并在网页提示原因（含上限、新包大小、可清退、差额），
  不删任何旧包、不动任何挂载，原附件照常下载。
- **入库前中断**：上传流先写到 spool 临时文件并实时算摘要，未提交事务则数据库
  无任何变化；残留 `.part` 在应用启动时清理，重启后原附件仍可下载。
- 包字节存于 SQLite（zeroblob + 增量 blob 写入，1 MiB 分块），与挂载、确认状态
  在同一库内，天然满足事务原子性与重启持久化。

## 实现结构

```
app/
  __init__.py       应用工厂；启动时建表、重核、清理残留分片
  db.py             SQLite 连接（WAL、外键、busy timeout）与建表
  core.py           匹配、重核/撤销、确认、CSV 解析与 upsert（不依赖 Flask）
  packages.py       诊断包接收、内容寻址入库、挂载、保护与 FIFO 清退（不依赖 Flask）
  views.py          页面、表单与诊断包上传/下载路由
  templates/        事件核对 / 导入 / 运行记录 / OOM 摘要 / 更正 / 诊断包 / 错误页
run.py              本地入口（gunicorn 用 run:app）
tests/selftest.py          归属/确认自测脚本
tests/package_selftest.py  诊断包留存/清退/原子性自测脚本
```

表：`runs`、`events`、`attributions`（重核结论）、`confirmations`（确认/撤销历史）、
`blobs`（内容寻址的诊断包字节）、`event_attachments`（事件↔包挂载，事件号主键）。

## 实测结果

- `python3 tests/selftest.py`（Flask test_client，临时库）：**51 项检查全部通过**，
  覆盖归属匹配、确认幂等、更正重核与撤销、旧页面拒绝、CSV 原子导入、重启持久化。
- `python3 tests/package_selftest.py`（同框架，配额调小到 1000 字节）：
  **73 项检查全部通过**，覆盖：
  - 配额解析（100M/2g/纯字节、非法值报错）、人类可读大小；
  - 上传/下载、同内容跨事件只存一份且按一份计字节、同事件重复上传只留一个挂载；
  - 换内容后旧包失去全部挂载即删除、共享包替换的挂载正确性；
  - FIFO 按首次入库顺序清退、腾够即停、被清退包的全部挂载一并移除；
  - 已确认事件挂载保护、腾不够整单拒收且旧包/挂载原样保留、原附件照常下载；
  - **接收文件期间确认派查**：以入库事务开始时的确认状态决定保护与清退；
  - 共享包仍有其他挂载时进入 FIFO 评估、受保护则拒收的边界场景；
  - 入库前中断（spool 残留启动清理、库零写入）、入库大小不符/事件不存在回滚；
  - 重启后附件与确认状态保留、HTTP 413 友好页、空文件拒收、已确认事件主动换挂。

另用 **gunicorn（2 worker）真实 HTTP 服务**做了端到端冒烟：导入 CSV →
同内容传两个事件（1 blob/300B/2 挂载，下载一致）→ 确认事件后传大包被拒收且
原附件可下载 → 解除确认后 FIFO 清退共享包并移除其全部挂载、新包入库可下载 →
杀进程重启后原附件仍可下载、spool 残留被清理 → 10 并发确认仅 1 条 active、
并发上传无 `database is locked`。

Docker 部分：本环境无 docker 守护进程，`docker-compose.yml` 已做 YAML 结构校验，
Dockerfile 经静态核对（依赖仅 flask+gunicorn，`run:app` 为模块级应用对象，
诊断包与 spool 都在 `/data` 命名卷内），**未实际构建镜像**，请在有 docker 的
机器上执行 `docker compose up -d --build` 验证。

## 余项 / 限制

- 无登录鉴权，假定部署在内网；如需可加反向代理 Basic Auth。
- 编号（run_no / event_no）全局唯一，多主机导入需各自编号段（或后续加主机维度）。
- 每次变更全量重核，万级事件以内无压力；更大数据量可改为按 boot_id 增量重核。
- 不支持删除记录（只能更正覆盖）；误录的编号可更正为占位值。
- scope 仅接受 `memcg`/`host` 两个标记，其他内核来源的表述需先归一化。
- 诊断包字节存 SQLite，适合本场景的中小型包；单包极大或留存上限调到 GB 级以上时，
  建议改为文件系统/对象存储 + 数据库只存索引（事务可改用"先写临时文件再改名"）。
- 生产用 gunicorn 多进程 + SQLite WAL 足够本场景；更高并发需换外部数据库。
